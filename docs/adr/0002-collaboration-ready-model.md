# ADR 0002: 협업으로 옮길 수 있는 보드 모델

- 상태: 채택
- 날짜: 2026-11-06

## 배경

처음에는 혼자 쓰는 로컬 우선 도구로 시작한다. 하지만 이벤트스토밍은 본래 여럿이 함께하는 워크숍이므로 실시간 협업(CRDT + 릴레이 서버)으로 옮길 가능성이 크다. 혼자 쓰는 앱의 흔한 가정(스냅샷 실행 취소, 상태 전체를 돌려주는 리듀서, 배열 순서, 증가형 ID)은 그 전환을 재작성으로 만든다. 부모-자식 트리처럼 위치를 구조에 묶어 두는 모델도 3자 병합을 복잡하게 만든다.

## 결정

1. **평평한 맵**: 보드는 `id → Sticky` 맵이다. 순서는 배열이 아니라 숫자 `z`다.
2. **필드 단위**: 스티키의 속성은 모두 독립 필드다. 여러 속성을 객체 하나에 묶지 않는다.
3. **랜덤 ID**: ID는 `crypto.randomUUID()`로 만들고, 도메인은 호출자에게 받는다.
4. **패치가 유일한 변경 경로**: 명령은 `Patch[]`(`add`, `set`, `delete`)를 돌려주고, 보드는 `applyPatches`로만 바뀐다. 아무것도 바뀌지 않으면 같은 참조를 돌려준다.
5. **역패치 기반 실행 취소**: 기록에는 스냅샷이 아니라 역패치를 둔다. 실행 취소는 이 편집기의 변경만 되돌리고 다른 곳의 변경은 남긴다.
6. **외부 변경에 관대함**: 없는 스티키에 대한 패치는 오류 없이 건너뛴다. 선택처럼 스티키를 가리키는 UI 상태는 보드에서 파생한다.
7. **객체 간 불변식 없음**: 여러 스티키에 걸친 규칙을 도메인에서 강제하지 않는다. 필요하면 경고로 보여 준다.
8. **저장소 인터페이스**: `BoardStore`(`load`, `apply`, `subscribe`) 뒤에 저장 방식을 숨긴다. 지금은 `LocalBoardStore`(localStorage, 다른 탭의 변경을 패치로 전달)를 쓴다.

## 결과

- 협업으로 옮길 때는 `BoardStore`를 Yjs로 구현해 바꿔 끼운다. `set`은 `Y.Map.set`, `add`와 `delete`도 1:1로 대응한다. 도메인, 세션, 화면은 그대로 둔다.
- Drive 저장을 붙일 때도 병합은 "스티키별, 필드별 비교"로 끝난다. 트리 병합이 필요 없다.
- 드래그 중 위치는 화면 상태로만 두고, 끝날 때 패치 한 묶음으로 커밋한다. 포인터가 움직일 때마다 기록이나 저장소에 쓰지 않는다.
